# Software Supply Chain & Risk Management: Study Guide

Same content as the interactive simulator (`risk-simulator.html`). Each topic lists its working principle step by step, pros and cons, and where it is used.

## Enterprise Risk Management (ERM)

Risk is handled as part of strategy, not as a separate chore. Five concerns feed one ERM process (COSO model; ISO 31000 is the companion standard).

### Working principle (step by step)

1. **Mission, Vision & Core Values**: Define what the organization stands for. This shows what is worth protecting and how much risk it will accept.
2. **Strategy Development**: Choose a strategy and check the risks each option adds against the organization's risk appetite.
3. **Business Objective Formulation**: Turn strategy into measurable goals. Each goal gets its own risks identified.
4. **Implementation & Performance**: Run the plan: identify, assess, prioritize and respond to risks, then track results against targets.
5. **Enhanced Value**: Review and report. Feedback improves later decisions and creates value for stakeholders.

### Pros

- Ties risk directly to strategy and goals
- Common risk language across departments
- Supports internal controls and audits

### Cons

- Heavy documentation and effort
- Needs strong executive sponsorship
- Generic; must be tailored to each organization

### Where it is used

- **Commercial:** Banks and insurers (enterprise risk, internal-control reporting), manufacturers, retailers.
- **Defense:** Defense contractors aligning program risk with contract objectives; ministries using ISO 31000-style risk policy.
- **Other:** Hospitals, universities, public agencies, NGOs.

## Risk Review Types

Reviews find and reduce threats in three areas. The framework is the 'how'; the same four questions apply to all of them.

### Working principle (step by step)

1. **Internal review**: Checks internal controls and processes. Frameworks: COSO ERM (2004, 5 phases, 20 principles) and ISO 31000 (2009). Inputs: audit reports, financial statements, compliance documents, risk policies, risk registers. Outputs: Risk Assessment Reports, control-effectiveness reports, action plans, treatment plans, monitoring schedules.
2. **Supplier review**: Assesses third-party vendor risk. Frameworks: NIST SP 800-161 (supply chain risk) and ISO/IEC 27036 (4 parts, incl. cloud). Inputs: supplier security assessments, contracts, compliance checklists. Outputs: risk reports, plans, compliance certificates.
3. **Architecture review (ARR)**: Finds security risk in IT design, implementation and maintenance. Uses NIST SP 800-53 controls, OWASP tools (Top 10, ZAP, SAMM), TOGAF (aligns IT with business) and ISO/IEC 27001. Outputs: security improvement plans, compliance reports.
4. **Common method: why, who, what, where**: Why: set context and purpose. Who: identify stakeholders. What: scan, assess, document. Where: implement controls and monitor continuously.

### Pros

- Structured, repeatable assessments
- Produces evidence for auditors and regulators
- Covers people, vendors and technology

### Cons

- Many overlapping frameworks to choose from
- Point-in-time unless monitoring is continuous
- Quality depends on input data and assessor skill

### Where it is used

- **Commercial:** Finance and cloud providers run vendor reviews and OWASP-based application testing; enterprises use TOGAF/ISO 27001.
- **Defense:** Federal and defense programs apply NIST SP 800-53 and 800-161 to systems and suppliers.
- **Other:** Healthcare, energy and government agencies for regulatory compliance.

## Software Supply Chain Risk Management

Software comes through layers of suppliers. Lower down, you control less and see fewer known vulnerabilities (CVE data covers popular products, not your custom code). Trust bars are illustrative.

### Working principle (step by step)

1. **Hardware & systems vendors**: Firmware and platforms from major vendors. Usually robust, trustworthy integrity and security processes.
2. **Application software providers**: Large vendors (COTS software) with secure, reliable update and support processes.
3. **Third-party developers**: Custom or tailored software. Engage only if both sides agree how security will be provided and assessed.
4. **In-house developers**: Formal QA, configuration management and security assessment give as much control as the organization funds.
5. **Open-source providers**: Support ranges from good to none; updates may not be digitally signed or verifiable.
6. **Citizen programmers**: Staff-written scripts and macros, often adapted from the internet. Powerful but hard to manage, verify or assess.

### Pros

- Layered view shows where to focus controls
- COTS and in-house code can be tightly governed
- Open source and citizen code give flexibility and speed

### Cons

- Visibility drops toward the bottom layers
- Custom code may be unknown to CVE databases
- Citizen code often skips security requirements

### Where it is used

- **Commercial:** Software vendors and enterprises track component origin (often with an SBOM, a list of components).
- **Defense:** Defense procurement vets suppliers and component provenance for mission systems.
- **Other:** Hospitals and utilities review vendor and open-source risk for critical systems.

## Source Systems for Risk Data

Any system that data passes through is in scope. Data from four categories shows risk level and exposure.

### Working principle (step by step)

1. **Applications**: SaaS email, CRM and ERP systems used to run the business.
2. **Security appliances**: Firewalls, IDS/IPS and SIEM devices (hardware or virtual) giving protection, visibility and monitoring.
3. **Network devices**: Routers, switches and access points that connect systems and networks, inside and outside.
4. **Hosts**: Workstations and mobile devices. They hold sensitive data and are common entry points to the network.

### Pros

- Wide coverage gives a fuller risk picture
- Logs and telemetry support evidence-based decisions

### Cons

- Large data volume needs automation
- Gaps in any category create blind spots

### Where it is used

- **Commercial:** Security operations centers feed SIEM tools with logs from all four categories.
- **Defense:** Cyber commands correlate network, host and appliance data for situational awareness.
- **Other:** Universities and city governments monitor endpoints and networks the same way.

## Software Supply Chain Controls

Controls that protect what you install, build and buy. Try the code-signing demo below the steps.

### Working principle (step by step)

1. **Mobile code**: Code that arrives from outside, whose development you cannot see or influence. Least trustworthy; filter it with antimalware, antivirus and intrusion detection.
2. **Code signing**: The package is hashed and the hash is signed with a private key (public-key algorithm). Receivers verify with the certificate. Do not install unsigned or unverifiable software.
3. **Shadow IT**: Hardware or software bought outside IT, usually without security review. Check licensing and how patches will interact. Gartner estimated about 35% of IT spend in 2020.
4. **Software restriction policies (SRP)**: Policy plus a technical block that stops unknown software from running, even for administrators. Path-based rules cover executables and libraries with little performance cost.
5. **Escrow**: A trusted third party holds the vendor's source code, released to the buyer only if the vendor fails (bankruptcy, ends support).
6. **Code ownership**: Source code and documentation are intellectual property. The contract must say who owns the finished product.
7. **Licensing**: Use software only as licensed (type and number of licenses, per the EULA). Breaches can bring fines or criminal charges.

### Pros

- Blocks tampered and unapproved software
- Protects continuity if a vendor fails
- Reduces legal and compliance exposure

### Cons

- Signing needs key and certificate management
- Strict SRP can slow legitimate work
- Escrow and contracts add cost and negotiation

### Where it is used

- **Commercial:** OS and app updates are signed; enterprises use application allow-listing; escrow for critical vendor software.
- **Defense:** Signed, allow-listed software on controlled systems; source escrow for long-life programs.
- **Other:** Banks, hospitals and app stores require signed code.

## Vulnerability Management Life Cycle

An exploited vulnerability existed before the attack; the defenders just did not know. The cycle finds, records and fixes them continuously.

### Working principle (step by step)

1. **Scan**: Automated tools scan networks, web apps, databases, endpoints, on-premises and cloud. Any change can trigger a rescan.
2. **Analyze & assess**: Experts judge which findings could cause a serious risk event. When in doubt, add it to the risk register until ruled out.
3. **Track**: Record every candidate in the tracking system. Keep suspected items; storage is cheap compared with a missed risk.
4. **Align to risks**: Link each vulnerability to an existing risk, or carry it unaligned until analysis finishes.
5. **Prioritize**: Leadership ranks risks by organizational goals, so aligned vulnerabilities inherit that priority. New risks get further assessment.
6. **Treat**: Schedule and complete fixes, then validate (often by testing). Then scan again.

### Pros

- Continuous, repeatable process
- Priorities follow business risk, not just severity scores
- Validation proves fixes worked

### Cons

- Scan results need expert analysis
- False positives consume time
- Hard to manage at scale without automation

### Where it is used

- **Commercial:** Enterprises and cloud providers run scheduled scans and patch cycles; regulated sectors such as payments require them.
- **Defense:** Mission networks run continuous scanning and risk-based patching.
- **Other:** Hospitals, utilities and universities patch by risk priority.

## Glossary: full forms

| Term | Full form | Meaning |
|---|---|---|
| COSO | Committee of Sponsoring Organizations of the Treadway Commission | Body behind the ERM framework focused on internal controls |
| ERM | Enterprise Risk Management | Managing risk across the whole organization, linked to strategy |
| ISO | International Organization for Standardization | Publisher of international standards |
| ISO 31000 | ISO risk management standard | Guidelines for understanding and treating enterprise risk |
| RAR | Risk Assessment Report | Management-facing result of a risk review |
| ARR | Architecture Risk Review | Review of IT architecture for security risk |
| NIST | National Institute of Standards and Technology | US agency publishing security guidance |
| SP 800-161 | Special Publication 800-161 | NIST guide to supply chain risk management |
| SP 800-53 | Special Publication 800-53 | NIST catalog of security and privacy controls |
| OWASP | Open Web Application Security Project | Nonprofit for software security; free tools |
| ZAP | Zed Attack Proxy | OWASP tool that tests web apps for flaws |
| SAMM | Software Assurance Maturity Model | OWASP model to measure and improve software security |
| TOGAF | The Open Group Architecture Framework | Aligns IT architecture with business goals |
| ISO/IEC 27001 | Information security management system standard | Requirements for an ISMS; suits larger enterprises |
| ISO/IEC 27036 | Information security for supplier relationships | Four-part standard incl. cloud services |
| ISMS | Information Security Management System | Policies and processes that manage information security |
| SCRM | Supply Chain Risk Management | Finding and reducing risk from suppliers and components |
| COTS | Commercial Off-The-Shelf | Ready-made software bought from vendors |
| CVE | Common Vulnerabilities and Exposures | Public catalog of known vulnerabilities |
| SBOM | Software Bill of Materials | List of components inside software (outside source text) |
| SOHO | Small Office / Home Office | Smallest environment type, still needs tracking |
| SRP | Software Restriction Policy | Rules that block unapproved software from running |
| EULA | End-User License Agreement | Contract stating allowed use of software |
| SaaS | Software as a Service | Cloud-delivered application |
| CRM | Customer Relationship Management | System for managing customer data |
| ERP | Enterprise Resource Planning | Software integrating core business processes |
| IDS/IPS | Intrusion Detection / Prevention System | Detects (and blocks) malicious activity |
| SIEM | Security Information and Event Management | Collects and correlates security logs and alerts |
| Shadow IT | Unsanctioned IT | Tech acquired without IT department knowledge |
| Escrow | Third-party custody | Source code held by a neutral party for the buyer's protection |
| Risk register | Risk register | Database of identified risks and linked vulnerabilities |
